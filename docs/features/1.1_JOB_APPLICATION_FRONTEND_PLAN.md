# Implementation Plan 1.1 — Frontend: Job Posting Page & Application Form (Web, Not Integrated with Backend)

- **Workstream:** 1 — HireFlow Job Application Screen (F-1.1, stories S-1.1.1–S-1.1.6)
- **User Story:** `docs/user-stories/1.1_JOB_APPLICATION_FRONTEND_USER_STORY.md`
- **Status:** Ready for Dev
- **Author:** Sanjeewa (Team Lead)
- **Created:** 2026-08-13

## 1. Summary
Build a single-page Angular experience presenting HireFlow's fixed job posting ("Senior .NET Engineer (Remote, UK)") and an application form (full name, email, CV upload, optional 500-char cover note) that validates client-side, persists a successful submission **only to browser `localStorage`** (no backend call — see PRD Non-Goal NG1), swaps the form for a name/email-echoing confirmation with a "start again" reset, and surfaces a genuine storage-failure error state. Layout, tokens, and responsive breakpoints (desktop ≥900px two-column / mobile ≤420px) must match `docs/design/Job Application Page.dc.html` and `docs/design/HireFlow Style Sheet.dc.html` 1:1. This story has **no API and no server-side component** — F-1.2 (backend submit API) is an independent, non-integrated workstream per PRD NG1.

## 6. Threat Model (STRIDE-lite — MANDATORY)
> Address every letter below. Keep each row 1–2 lines. Reviewer validates these are implemented.

| STRIDE | Applies? | Risk in this feature | Mitigation / control |
|---|---|---|---|
| **S**poofing (identity) | N | No authentication/identity concept exists — candidate is anonymous and unauthenticated by design (PRD has no auth requirement for this story). | N/A — no identity to spoof; do not add any ad-hoc "remember me"/identity cookie. |
| **T**ampering (integrity) | Y | A candidate (or malicious script) could bypass client-side validation to submit an invalid/oversized/wrong-type CV description, or tamper with `localStorage` records directly via devtools. | Enforce CV type/size checks in `cv-file-validation.util.ts` before accepting the file (never trust the `accept` attribute alone); treat `localStorage` as candidate-owned, single-browser data with no integrity guarantee beyond this — no server trusts it, so tampering only affects the tamperer's own browser. |
| **R**epudiation | N | No audit trail is required — there is no server, no other party, and no multi-user visibility of the data (User Story §5). | N/A for this phase; not applicable until/unless a backend integration is added (explicitly out of scope, PRD NG1). |
| **I**nformation Disclosure | Y | Candidate PII (name, email, cover note, CV metadata) sits in `localStorage`, readable by any script running on the same origin (XSS) or by anyone with physical/devtools access to that browser profile. | Render all candidate-supplied text (name, email, cover note) via Angular property/interpolation binding only — never `[innerHTML]`, `bypassSecurityTrust*`, or string-concatenated DOM; never log PII to the console; never persist the CV's actual file bytes (metadata only, per FR-FORM-3). |
| **D**enial of Service | Y | An oversized CV file read into memory, or an unbounded cover note, could freeze the tab or bloat `localStorage` until it throws. | Enforce the 500-character cover-note cap and the 10MB/type CV cap client-side *before* any file read or state write; treat a `setItem` quota exception as the expected, handled `StorageUnavailableError` path (S-1.1.5), never an unhandled crash. |
| **E**levation of Privilege | N | No roles, permissions, or privileged actions exist on this public page. | N/A. |

### 6.1 Assets & Trust Boundaries
- Sensitive data in this feature: candidate full name, email address, optional cover note, and CV metadata (file name, size, type — never file contents).
- Trust boundary crossings: none cross an origin/server boundary — the only boundary is the browser's JS execution context writing into that same origin's `localStorage`. No network call, no backend, no third party ever receives this data in this phase.

### 6.2 Pre-emptive OWASP mapping
- Likely-in-play: **A03** (Injection/XSS — via re-rendering candidate-supplied name/email/cover-note text if ever bound unsafely), **A09** (Security Logging — must never log PII to console/telemetry). Reviewer will still do a full A01–A10 pass.

## 7. Test Strategy
- Unit tests: `cv-file-validation.util.spec.ts` (accepted/rejected types, boundary sizes at/over 10MB); `application-form-validators.util.spec.ts` (required name, required+format email, required CV, valid/invalid email patterns); `job-application-storage.service.spec.ts` (successful write/read round-trip, and a mocked `localStorage.setItem` throw surfacing `StorageUnavailableError`).
- Integration tests: N/A — no endpoints/auth/tenant paths exist in this story.
- Frontend component tests: `job-posting-details.component.spec.ts` renders all fixed content sections (AC-1); dead-link behaviour on header/confirmation "browse roles" links performs no navigation (AC-2); `application-form.component.spec.ts` covers live character counter and 500-char hard cap (AC-3), CV accept/reject messaging (AC-4/AC-5), submit-blocked + flagged-fields + banner on invalid submit (AC-6), flag-clears-on-correction without re-submit (AC-7); `application-confirmation.component.spec.ts` covers greeting/echoed email/next-steps on success (AC-8) and full reset via "start again" (AC-9); storage-failure error rendering only on a genuine thrown exception, never via any hidden toggle (AC-10).
- Negative tests MUST cover: missing name, missing/invalid-format email, missing CV, oversized CV (>10MB), disallowed CV type, cover note at/over 500 chars, and a forced `localStorage` exception.

- If any diagnostic logging is used during development, it must be PII-free, generic event names only (e.g. `cv_rejected`, `application_saved`, `application_save_failed`), gated behind `environment.production === false`, and removed/silenced for production builds.
- Correlation id propagation: N/A — no server call exists to correlate against.

## 9. Risks & Trade-offs
- R1: Persistence and validation logic here will need to be re-derived (not reused) if/when a future PRD revision integrates this frontend with the F-1.2 backend API — accepted per PRD NG1/OQ2; do not pre-build integration hooks now.
- R2: `localStorage` records accumulate indefinitely across submissions in the same browser with no built-in cap or cleanup (PRD OQ1 treats this as accumulate-only) — acceptable for this demo phase; not a production data-retention design.

## 10. Out of Scope
- Any communication with, or dependency on, a backend service (PRD NG1) — nothing is transmitted anywhere.
- Any real destination behind either "browse other open roles" link.
- Multiple job postings, browsing/searching roles, or dynamic job content.
- Any way to view, search, or manage submitted applications after the immediate on-screen confirmation.
- Any account creation, sign-in, or identity verification.
- Any real data-retention or deletion behaviour beyond presentational copy.
- Any manual/hidden mechanism to simulate a storage failure.
- Building the reference-only mobile/wireframe design files as separate experiences — one responsive experience only.
