# User Story 1.1 — Frontend: Job Posting Page & Application Form (Web, Not Integrated with Backend)

- **Workstream:** 1 — HireFlow Job Application Screen (F-1.1, stories S-1.1.1–S-1.1.6)
- **Traces to PRD:** FR-JOB-1, FR-JOB-2, FR-FORM-1, FR-FORM-2, FR-FORM-3, FR-FORM-4, FR-FORM-5, FR-FORM-6, FR-PERSIST-1, FR-PERSIST-2, FR-PERSIST-3, Non-functional — Design fidelity
- **Status:** Ready for Review

- **Created:** 2026-08-13

## 1. Story
As a **candidate**, I want **to view the fixed job posting and submit an application (name, email, CV, optional cover note) entirely within my browser, with clear validation and a confirmation of success**, so that **I can apply for the role and know my application was received, without needing any backend service to be available**.

## 2. Business Context
This delivers the complete candidate-facing experience for HireFlow's single job posting demo: reading the role details and submitting an application. Per the PRD, this frontend flow must work end-to-end using only client-side storage — it does not call any backend service in this phase, so the candidate's experience of "apply and get confirmed" must be fully self-contained. It also must visually and behaviourally match the approved design so the demo is a faithful representation of the intended product.

## 3. Scope
### 3.1 In Scope
- Presenting the fixed job posting: role title, summary, key facts (salary, location, contract type, team, application closing date), hiring manager information, and the descriptive body content (what the candidate will do, what's expected of them, and how the hiring process works).
- A non-functional "browse other open roles" link in the page header — it is present for visual completeness but does not lead anywhere in this demo.
- An application form capturing: full name, email address, CV, and an optional cover note limited to 500 characters with a running character count visible to the candidate.
- Uploading a CV either by browsing for a file or by dragging a file onto the upload area, accepting only PDF, DOC, or DOCX files no larger than 10MB.
- Retaining only descriptive information about the uploaded CV (its name, size, and type) — never the file's actual contents.
- Validating the form when the candidate attempts to submit: full name and email are required, email must be in a valid email format, and a CV must be attached. Once the candidate has attempted to submit, invalid fields are clearly flagged as the candidate continues to correct them.
- A clear, prominent indication (in addition to any per-field flags) when the overall submission cannot proceed because required information is missing or invalid.
- On a successful submission: saving the candidate's application details (name, email, cover note, CV description, and when it was submitted) so the candidate's confirmation can be shown reliably; replacing the form with a confirmation message that greets the candidate by name, repeats back the email they applied with, and explains what happens next; and a non-functional "browse other open roles" link on the confirmation as well.
- A "start again" action from the confirmation screen that clears the form completely (all fields, any error indicators, and the selected CV) so the candidate can submit a fresh application in the same visit.
- A visible, honest error state if the candidate's application genuinely cannot be saved because their browser's storage is full or unavailable (e.g. private/incognito browsing) — this must only ever be shown as a result of a real storage failure, never as a deliberately triggered demo/test state.
- A layout and visual presentation (colours, typography, spacing, and general look and feel) consistent with the approved design, that adapts appropriately between a wider desktop view and a narrower mobile view.

### 3.2 Out of Scope (explicit)
- Any communication with, or dependency on, a backend service — the application is saved only within the candidate's own browser and nothing is transmitted elsewhere in this phase.
- Any real destination behind the "browse other open roles" links — they remain non-functional for this demo.
- Multiple job postings, browsing/searching roles, or any dynamic job content — the posting shown is fixed, single content for this demo.
- Any mechanism for a candidate, recruiter, or anyone else to view, search, or manage applications after submission (beyond the immediate on-screen confirmation).
- Any account creation, sign-in, or identity verification for the candidate.
- Any real data-retention or deletion behaviour — retention/deletion messaging shown to the candidate is presentational only.
- Any manual or hidden way to simulate a storage failure for testing/demo purposes — only a genuine failure may trigger the error state.
- Implementing the reference-only mobile and wireframe design materials as separate experiences — one single responsive experience is delivered.

## 4. Acceptance Criteria (Given/When/Then)
> Every AC MUST be independently testable, phrased as observable business behaviour
> (never as implementation steps — no table/field/endpoint/component names). Use stable
> ids so the reviewer can map PASS/FAIL per AC.

- **AC-1** — Given a candidate opens the job application page, when the page loads, then the candidate sees the complete fixed job posting content (title, summary, key facts, hiring manager information, and all descriptive body sections) matching the approved design.
- **AC-2** — Given the candidate is viewing the job posting page or the confirmation screen, when they select the "browse other open roles" link, then no navigation occurs (the link performs no function), consistent with this being a single-posting demo.
- **AC-3** — Given the candidate has not yet attempted to submit the form, when they type into the cover note field, then they see a live, accurate count of how many of the 500 allowed characters they have used, and they cannot exceed that limit.
- **AC-4** — Given the candidate selects a CV file that is a PDF, DOC, or DOCX no larger than 10MB, when they choose it via browsing or drag-and-drop, then the file is accepted and the candidate sees a description of the selected file (its name and size) rather than the file being immediately submitted anywhere.
- **AC-5** — Given the candidate selects a file that is not one of the accepted types, or that exceeds 10MB, when they attempt to select it, then the file is rejected and the candidate is shown a clear reason why.
- **AC-6** — Given the candidate attempts to submit the form with the full name missing, the email missing or not in a valid email format, or no CV attached, when they select submit, then the submission does not proceed, the specific invalid field(s) are visibly flagged, and a clear overall notice indicates the application cannot be sent until the issue(s) are fixed.
- **AC-7** — Given the candidate has already attempted to submit and has one or more invalid fields flagged, when they correct a flagged field to a valid value, then that field's flag clears without requiring another full submit attempt.
- **AC-8** — Given the candidate provides a valid full name, valid email, and a valid CV (with or without a cover note), when they submit the application, then their application details are successfully saved for this browser and the form is replaced with a confirmation that addresses the candidate by their first name, repeats back the email they applied with, and describes the next steps.
- **AC-9** — Given the candidate is viewing the confirmation screen, when they select "start again", then they are returned to a completely empty, error-free application form ready to accept a new application.
- **AC-10** — Given the candidate's browser storage genuinely cannot accept the application (for example because it is full or unavailable, such as in private browsing), when the candidate submits an otherwise valid application, then a clear, honest error message is shown explaining the application could not be saved, and there is no way to deliberately trigger this state outside of a genuine storage failure.
- **AC-11** — Given the candidate is using a wide desktop-sized browser window, when they view the job posting page, then the job content and application form are presented in the design's two-column layout; given the candidate is using a narrow mobile-sized browser window, when they view the same page, then the content is presented in the design's single-column, stacked layout — with visual styling (colour, type, spacing) consistent with the approved design across both.

## 5. Security & Privacy Notes (business-level only)
- Sensitive data involved: the candidate's full name, email address, an optional cover note, and descriptive information about their CV (file name, size, and type — never the file's actual contents).
- This information is saved only within the submitting candidate's own browser for this demo phase; it is not transmitted to, or visible from, any other system, device, or person. No one other than the candidate on that browser/session should be able to view or change their own submitted application data through this experience.

## 6. Dependencies
- Upstream stories / workstreams: None — this is the first story for workstream 1.
- External systems: None. This story is explicitly independent of the standalone backend submit capability being delivered under Feature F-1.2; the two are not integrated in this phase.
